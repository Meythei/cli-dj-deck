## D1. Python のバージョン: 3.13

- **決めたこと**: CPython 3.13(開発機では 3.13.14)。`.venv` は `py -V:Astral/CPython3.13.14 -m venv .venv` で作り直した
- **他の案**: 3.12(3.12.13)
- **理由**: 2026-09-16 時点の PyPI で、使う依存すべてに 3.13 の Windows 向け wheel があることを確認し、実際に 3.13 の venv へ入れて import・`time_stretch`・デバイス列挙まで動かした
  - numpy 2.5.3 / scipy 1.18.1 / librosa 1.0.0 は `requires_python >=3.12`
  - pedalboard 0.9.25、numba 0.67.0、llvmlite 0.49.0、msgpack 1.2.2 に cp313 win_amd64 wheel あり
  - soxr 1.1.0 は cp313 専用 wheel はないが abi3 wheel で入る
  - sounddevice 0.5.6、soundfile 0.14.0 は PortAudio/libsndfile 同梱の `py3-none-win_amd64`
  - 3.13 では `multiprocessing.shared_memory.SharedMemory(track=False)` が使えるので、子プロセスが共有メモリにアタッチしたときの resource_tracker の誤警告・誤解放(Linux/macOS)を避けられる
  - 3.12 より 3.13 を選ばない理由は見つからなかった
- 開発機の `py` ランチャーには 3.10/3.11 しかなかったため、uv(`uv python install 3.13`)で入れた。uv が PEP 514 でレジストリ登録するので `py -V:Astral/CPython3.13.14` で呼べる。python.org の 3.13 を入れた環境では `py -3.13` でよい

## D2. 設定・データ・キャッシュの置き場所

- **決めたこと**: `platformdirs` のユーザーディレクトリ(`appauthor=False`)。Windows では次のとおり
  - 設定: `%LOCALAPPDATA%\cli-dj\config.toml`(初回起動時にコメント付きの雛形を書く)、手動補正 `overrides.json` も同じ場所
  - データ: `%LOCALAPPDATA%\cli-dj\library.json`、`analysis\<track_id>.json` / `.env.npy` / `.failed.json`、`logs\`
  - キャッシュ: `%LOCALAPPDATA%\cli-dj\Cache\renders\`(フェーズC)
  - 環境変数 `CLIDJ_HOME` があれば、その下の `config/ data/ cache/` に全部まとめる。テストは `tests/conftest.py` で全テストに一時ディレクトリを割り当て、開発者の実データに触れない
- **他の案**: リポジトリ内 `.cache/`(指示書でリポジトリ外と決まっている)、`~/.clidj/` 一か所(OS の慣習に反し、Windows のバックアップ・掃除ツールとも相性が悪い)
- **理由**: Windows ではローミングしない `Local` が、数百MBになり得る解析・レンダリング結果の置き場として適切。config と overrides は人が編集・バックアップするものなので同じ場所に置き、再生成できるものは `Cache` に分けた
- `overrides.json` は JSON(`tomllib` は読み込み専用で、TOML の書き出しに依存を増やしたくない)。キーは track_id、人が読めるよう `title` も入れる

## D3. トラックの識別子と番号

- **決めたこと**: `track_id` = blake2b(ファイルサイズ + 先頭 64KiB + 末尾 64KiB) の 20 桁 hex。一覧の番号(`snip(3, ...)` の 3)は初めて見つけた順に振って `library.json` に保存し、再スキャンでも振り直さない
- **他の案**: ファイル全体のハッシュ(大きなライブラリで初回スキャンが遅い)、パス(移動で解析結果が失われる)、タイトル順の番号(1曲足すと後ろの番号が全部ずれ、セットファイルの `snip(番号)` が別の曲を指す)
- **理由**: 移動・リネームに強く、再エンコードやタグ以外の編集では変わる。同じ中身のファイルが2か所にあれば同じ曲として扱う(先に見つけたパスを使う)
- 変更されていないファイル(パス・サイズ・mtime が一致)はハッシュを再計算しない
- タグ(タイトル・アーティスト)は `mutagen`(1.48.1、2026-06 リリース、pure Python)。タグがなければファイル名の `Artist - Title` から取る

## D4. BPM・ビートグリッド・キー・ラウドネスの推定方法

- **決めたこと**
  - 解析用に 22050Hz モノラルへ変換(`librosa.resample`、soxr)。ラウドネスだけは元のサンプルレート・チャンネルで計算する
  - BPM: `librosa.onset.onset_strength`(hop 128 ≈ 5.8ms)→ `librosa.feature.tempo` で粗推定 → 設定の範囲 `[bpm_min, bpm_max)`(既定 88〜176)にオクターブで折りたたむ → 「オンセット包絡を拍周期で折りたたんだヒストグラムのピークが最も鋭くなる BPM」を ±4% を 0.02 刻み、±0.03 を 0.001 刻みで探す
  - 位相: 折りたたみヒストグラムのピーク → その位相と半拍ずらした位相のうち、120Hz 以下の帯域のエネルギーが大きい方を拍とする(キック側)→ 1ms 刻みのピーク包絡を折りたたみ、±40ms の範囲で立ち上がりが最も急な位置に合わせる
  - 最初の拍: 10ms RMS が曲の最大から -35dB 以内になった時刻以降で最初のグリッド位置(60ms の先行を許容)
  - キー: `chroma_cqt` の時間平均を Krumhansl-Kessler のプロファイル 24 種と相関 → Camelot
  - ラウドネス: ITU-R BS.1770-4 の K 特性(任意のサンプルレート用の双一次変換式)+ 400ms ブロック・絶対/相対ゲートを scipy で実装
- **他の案**: `librosa.beat.beat_track` の拍時刻を線形回帰(試作では BPM 124.53、最初の拍 +19ms。初回の numba JIT が 9 秒)、`pyloudnorm`(最終リリース 2026-01。数十行なので依存を増やさなかった)
- **理由**: 一定テンポの曲だけを対象にするなら、曲全体を1本のグリッドとして当てはめる方が、拍ごとに推定して回帰するより精度が出る。合成トラック(100〜150BPM、最初の拍 0〜2秒、45〜150秒、キック・オフビートのハット・オフビートのベース・コードのある構成)24本で、BPM 誤差最大 0.020、最初の拍の誤差最大 5.4ms(許容 ±0.1 / ±10ms)
- 途中で見つかった問題と対処(いずれも回帰テストあり)
  - 「オンセットが強い最初の拍」を拍0にすると、キックだけの静かなイントロが飛ばされた(90秒の曲で拍0が30.4秒)→ 無音判定に変更
  - ハットとオフビートのベースが多いと位相が半拍ずれた → 低域エネルギーで表裏を判定
- **既知の限界**: ダウンビート(小節の1拍目)は推定していない。拍0が小節頭でない曲は `regrid(n, offset_ms=...)` で直す。キック以外が低域を支配する曲では表裏判定を誤る可能性がある。合成音源でのキー推定は、コードの鳴らない区間が長いと外れやすい(実データでは要確認)
- 既定の BPM 範囲 88〜176: ハウス・テクノ・トランス(120〜140)、ドラムンベース(174、87と出がち)、ヒップホップ(88〜110)が素直に入る。85BPM 前後のダウンテンポは倍になるので、必要なら config で範囲を変えるか `regrid(n, bpm=...)` で直す

## D5. 波形データの保存形式

- **決めたこと**: 解析では時間基準のピーク包絡(22050Hz で 128 サンプル ≈ 5.8ms ごとの最大値、float32 の `.npy`)を保存する。UI が使う拍基準(1拍16点、既存の `SAMPLES_PER_BEAT`)の波形は、有効なグリッド(overrides 込み)で読み込み時に変換する(1曲数ms、表示するまで遅延)
- **他の案**: 指示書どおり拍基準の配列そのものを保存する
- **理由**: 拍基準で保存すると `regrid()` のたびに音声ファイルをデコードし直す必要がある。「自動解析は必ず外れる前提」(指示書6章)なので、補正を安くする方を選んだ。UI から見える解像度は拍基準のままで、指示書の意図(拍の頭が見える波形)は変わらない

## D6. バックグラウンドワーカー

- **決めたこと**: 解析(とフェーズCのレンダリング)は `ProcessPoolExecutor`(spawn、既定2プロセス)、フォルダ走査は UI プロセスのスレッド1本。結果はワーカーがファイルに書き、UI プロセスには小さな dict だけ返す。UI は描画ティックで `Session.poll()` を呼んで完了分を反映する(ワーカーのスレッドから UI の状態を触らない)
- ワーカーは起動直後に fd 1/2 を `logs/workers.log` に付け替える。Windows では spawn した子プロセスが親のコンソールを共有するため、デコーダや numba の警告1行で Textual の画面が壊れる
- ワーカーが落ちたら(`BrokenProcessPool`)そのトラックを失敗として `.failed.json` に記録し、次のジョブからプールを作り直す。`scan(retry=True)` で失敗したトラックを再解析する
- **他の案**: スレッドで解析(librosa/numba は GIL を離す区間が多いが、UI の描画と取り合う)、asyncio + subprocess(ジョブの受け渡しを自前で書くことになる)

## D7. タイムストレッチのエンジンと設定(許容誤差に関わる)

- **決めたこと**: `pedalboard.time_stretch(high_quality=False, use_long_fft_window=False)` = Rubber Band の R2 エンジン + 短い FFT 窓(Rubber Band の percussive 設定)。さらに比率ごとの一定のずれを、クリック列を一度ストレッチして実測し、切り出し位置で補正する(`render.stretch_offset_samples`、ワーカー内で比率ごとにキャッシュ)
- **他の案と実測**(48kHz、クリック/キック、しきい値 30% の立ち上がり位置と理想の拍位置の差)
  - `high_quality=True`(R3、既定): 比率に応じて **拍ごとに累積するずれ**。124→128 で 0.175ms/拍(96拍で約17ms)、100→128 で -0.66ms/拍(最大60ms)。比率をわずかに変えると傾きが不規則に跳ぶ(1.0323 で +0.18、×(1+3e-3) で -0.29)ため、補正係数も作れない。出力の総サンプル数は要求どおりなので、長さだけ見ても気づけない
  - R2(長い窓): 累積ずれなし(傾き ±0.0003ms/拍)、比率に応じた一定のずれ ≈ 23ms×(1−1/f)(124→128 で +0.9ms、174→128 で -8.3ms)。ただし短いクリックでは拍ごとのゆらぎが最大 4.9ms(120→132)
  - R2(短い窓): 一定のずれは同様、ゆらぎはクリックで最大 0.7ms、キックで 0.6ms
  - `python-stretch`(Signalsmith Stretch、2025-02 以降リリースなし)、`audiotsm`(2017)、`pyrubberband`(外部バイナリが必要)は、メンテナンスか Windows での導入性で見送り
- **理由**: 原則3(予定された拍のサンプルちょうど)と 11章の ±3ms を満たすのは R2 + 補正だけだった。R3 は音質が良いとされるが、タイミングが崩れるのは DJ ツールとして致命的。音質差(特に短い窓による低域のにじみ、ストレッチ率が大きいときのトランジェント)は数値で判定できないので `docs/listening-checklist.md` の確認項目にする
- **許容誤差**: 11章の ±3ms はそのまま。テストは 124→128、128→124、120→132、140→128 × クリック/キック、32拍で最大 0.7ms 程度

## D8. レンダリング済みスニペットの形式・長さ・端の処理

- **決めたこと**
  - 元ファイルから「スニペット範囲 ± 1拍」を元のサンプルレートで読み、必要なら soxr(VHQ)で 48kHz にしてからストレッチする(`AudioFile.resampled_to` のシーク位置に頼らないため)。ファイルの前後にはみ出した部分は無音で埋める
  - 長さは `round(length_beats × 60 / set_bpm × sr)`。切り出し開始は小数サンプル位置を四捨五入(誤差 ≤ 0.5 サンプル = 10μs)
  - 同 BPM ではストレッチを通さない(サンプル単位で元ファイルと一致することをテスト)
  - 非ループ: 先頭・末尾 3ms の raised-cosine フェード。先頭サンプルは 0 にしない(「予定サンプルから鳴り始める」をテストで確認できるように)
  - ループ: ループ終端の直後の音 10ms を先頭 10ms に raised-cosine でクロスフェード。終端→先頭の遷移が元の音の自然な続きになる
  - ラウドネス補正ゲインは焼き込まない。`10^((目標 − 曲の統合ラウドネス)/20)`、持ち上げは最大 +12dB。エンジンがボイスのゲインとして掛ける。目標値を変えてもキャッシュが無効にならない
  - ゲインは曲単位の統合ラウドネスから求める(plan.md 冒頭 #5)。スニペット単位で揃えるとブレイクや riser がドロップと同じ音量になるため
- キャッシュキー: blake2b(track_id、グリッド(BPM・拍0の秒)、開始拍、長さ、ループ、セットBPM、サンプルレート、レンダラのバージョン)。パスは含めない(中身は track_id で決まる)。`<cache>/renders/<key>.npy` + `<key>.json`、一時ファイル → `os.replace` で書く。既存のキーは上書きしない(Windows ではエンジンが mmap 中のファイルを置き換えられない)。`regrid()` はキーが変わるので自動的に別ファイルになり、そのトラックの定義済みスニペットを再レンダリングする
- 古いキャッシュの掃除は未実装(既知の制限)

## D9. 準備待ちの保留と BPM 変更の制御

- **決めたこと**
  - スニペットの準備状態は (スニペット, BPM) ごと。`snip()` 評価時に現在の BPM(と変更待ちの BPM)でレンダリングを投げる
  - 再生コマンドは「発火した時点」で準備済みかを確認する。未準備なら保留して警告し、準備完了を `Session.poll()` が検出したら、そのコマンドを通常のクオンタイズでもう一度出す(= 準備完了後の最初の区切り。停止中なら即時)。レンダリングに失敗したら保留を破棄してエラー
  - `bpm(x)` は定義済みの全スニペット(`Session.snippets`、変数を再代入しても過去のスニペットを含む)を x でレンダリングし、全部が「済」か「失敗」になったら次の小節頭に切り替えを予約する。失敗があればエラーを出したうえで切り替える(失敗したスニペットはその後保留→破棄になる)
  - 失敗したジョブは自動では再投入しない(ポーリングのたびに壊れたファイルを投げ直さないため)。`prep()` が失敗分も再試行する
- **他の案**: コマンド入力時点で判定する(`at(33, ...)` のように、入力時は未準備でも 33小節目までに間に合う場合を保留にしてしまう)
- 事前に音声ファイルのないデモ曲は、最初に必要になった時点でワーカーが `clidj.synth` で決定的に合成して `<cache>/demo-audio/` に書き、その後にレンダリングする。`--demo` でも実際の音で試せるようにするため(plan.md 冒頭 #13)

## D10. EQ とリミッタの実装方法

- **決めたこと**
  - EQ: DJ ミキサー型の3バンドアイソレータを scipy で自前実装(`clidj/engine/dsp.py` の `Isolator3`)。Linkwitz-Riley 4次のクロスオーバー(250Hz / 2.5kHz)で low / mid / high に分け、帯域ごとに 0.0〜1.0 のゲインを掛けて足す。low 帯域には 2.5kHz の2次オールパスを通して位相を揃えるので、全ゲイン 1 で振幅特性は平坦(40Hz〜10kHz で ±0.1dB をテスト)。0 にするとその帯域は消える(60Hz サインに lo=0 で -30dB 以下をテスト。計算上は約 -49dB)。フィルタ係数は固定で `scipy.signal.sosfilt` を状態(zi)付きでブロックごとに回し、動かすのはゲインだけ(5ms の線形ランプで平滑化)
  - リミッタ: `pedalboard.BrickwallLimiter`(天井 -1dBFS、リリース 100ms、先読み 5ms)を `reset=False` でブロックごとに回し、最後に `np.clip(-1, 1)`。先読み分の遅延(48kHz で 240 サンプル)は起動時にインパルスで実測し、FIFO で固定遅延にする。オフラインレンダリングはその分を詰め、プレイヘッド表示は出力レイテンシに足す
- **他の案**
  - EQ に pedalboard の `LowShelfFilter` / `PeakFilter` / `HighShelfFilter`: シェルフのゲインを -∞ まで下げる「カット」が作れない。ゲインを動かすとフィルタ係数が変わり、平滑化の中身が pedalboard(JUCE)任せになってジッパーノイズの有無をテストで保証しにくい
  - リミッタに `pedalboard.Limiter`: JUCE の `dsp::Limiter` で、-10dB から常に圧縮がかかりメイクアップゲインも外せない(pedalboard のドキュメントにも「ラウドネスを上げるためのもの」とある)。DJ のマスターでは音が変わってしまう
  - リミッタを numpy で自前実装: 先読み + 瞬時アタック + 指数リリースはサンプルごとの再帰になり、ベクトル化すると近似になる。numba で書けば正確だが、JIT のウォームアップをオーディオプロセスの起動に持ち込むことになる
- **理由**: 指示書 7章の要件(lo/mid/hi を 0〜1 で絞れ、0 でほぼカット、ジッパーノイズなし、出力が 0dBFS を超えない)を、テストで数値的に保証できる方を選んだ。処理コストは 4レーン + EQ + リミッタ + オートメーションで 512 サンプルあたり平均 1.25ms(ブロック時間 10.67ms の 11.7%、p99 1.9ms)

## D11. エンジンの時刻・イベント・ボイスの扱い

- **決めたこと**
  - 拍 → サンプルは `TempoMap`(区間ごとに一定テンポ)。拍 b のイベントは `floor(exact + 0.5)` のサンプルで起きる。エンジン・オフラインレンダラ・テストが同じ丸めを使う
  - ブロックは「次のコマンドの拍・オートメーションの終わり・ワンショットの終わり」のサンプルで分割して処理する(ブロックサイズに関係なく同じサンプルで起きることをテスト)
  - ボイスの再生位置は毎サンプル拍から計算する(`(拍 − 開始拍) mod 長さ × 1拍のサンプル数`)。ループのたびの丸めは累積しない。バッファ長が小数サンプルの場合、ループの継ぎ目で1サンプル分の飛び/重複が起きる(継ぎ目はレンダリング時のクロスフェードで滑らかにしてある)
  - ボイス開始は予定サンプルから 1ms のランプ(最初のサンプルから非0)。停止・差し替え・BPM 切替では古いボイスを「元の位置から自走する 5ms のフェードアウト」に移す。BPM 切替の新しいボイスは 5ms でフェードイン(= 5ms のクロスフェード)
  - 遅れて届いたコマンドは次のブロックの先頭で適用し、拍の位置は予定どおり(= グリッドに乗ったまま、最初の数msが欠ける)。件数と最大遅延を数える
  - `stop()` は一時停止。位置を保ったまま音をフェードアウトし、`start()` で同じ位置からフェードインで再開する
  - 同じレーンのオートメーションは新しいもので置き換える。手動の `gain()` はその時点の値から引き継いでオートメーションを止める
  - レンダリング済みバッファは `np.load(mmap_mode="r")` で開き、コールバックの外(コマンドを受けるスレッド)で全ページを一度読んでおく
- `--no-audio`(ビジュアルのみ)も同じ `Engine` を `render_audio=False` で使う。音声の配列を作らず、状態遷移とイベントのタイミングだけを進める。タイミングの実装を1つにするため(plan.md の方針)

## D12. エンジンプロセスとプロセス間通信

- **決めたこと**
  - エンジンは `multiprocessing`(spawn)の子プロセス `clidj-engine`。UI → エンジンは `multiprocessing.Queue` に `(送信時刻 perf_counter_ns, EngineCommand)` を積む。エンジン → UI は `multiprocessing.shared_memory` の float64 配列(ヘッダ 29項目 + レーンごと 15項目)を seqlock で公開し、UI は描画のたびにコピーして読むだけ
  - エンジンプロセス内: コマンド受信スレッド(キュー読み、バッファの mmap と全ページの先読み)と、オーディオのコールバック(PortAudio のスレッド、または NullBackend のスレッド)に分ける。受け渡しは `collections.deque` の append / popleft(ロックなし)。`sys.setswitchinterval(0.0005)` で、コマンドスレッドが GIL を長く持たないようにする
  - コールバックは `engine.process()` → 出力バッファに書く → 状態配列に書く、だけ。例外は捕まえて無音にし、件数を状態に出す
  - 終了: UI の `close()` が `Shutdown` を送り、3秒待って `terminate` → `kill`。`atexit` にも登録。エンジンは SIGINT を無視し(Ctrl+C は UI が受けて終了処理をする)、50ms ごとに親プロセスの生存を確認して、UI が異常終了したら自分で抜ける。UI 側は状態配列のハートビート(最後の書き込み時刻)が 2秒止まったら「エンジン停止」とみなし、以後の送信は捨てる(例外にしない)
  - バックエンド: `SoundDeviceBackend`(既定は WASAPI の既定出力、`WasapiSettings(auto_convert=True)`、`latency="low"`)、`NullBackend`(実時間ペースで回し、次のブロックの締め切りまでに終わらなかったらアンダーラン1回)。デバイスが開けなければ NullBackend に切り替えて UI にエラーを出す(アプリは動き続ける)
  - `--no-audio` と `render` は同じ Engine をプロセス内で使う(D11)
- **他の案**: エンジンを UI と同じプロセスのスレッドにする(指示書で不可。Textual の描画が GIL を握る間にコールバックが待たされる)、状態も Queue で返す(UI が読むたびにキューを空にする必要があり、遅れて古い状態を表示しがち)、Pipe(Queue と大差なく、フィーダスレッドがない分 send がブロックし得る)
- エンジンプロセスは起動後に `gc.collect(); gc.freeze(); gc.disable()` し、循環 GC はコマンドスレッドが 30秒ごとに世代1だけ回す(実測 0.01〜0.2ms)。Windows では優先度クラスを HIGH、`timeBeginPeriod(1)`、NullBackend のスレッドは TIME_CRITICAL にする(いずれもこのプロセスだけの設定で、システム設定は変えない)
- UI プロセスも起動後に `gc.freeze()`。レーンの波形描画を numpy でベクトル化し、Rich の Text にはスタイルの連続ごとにまとめて追加する(描画結果は文字・スタイルともに変更前と一致することを確認)。1ティック 5.9ms → 2.5ms、ティック間隔の最大 110ms → 49ms
- **実測(開発機: Ryzen 5 5600 / 28GB、Windows 11、Python 3.13。Chrome・Discord・Overwolf などが同時に起動した普段の状態)**
  - 起動: NullBackend 1.3秒、WASAPI 1.8秒(numpy/scipy/pedalboard の import を含む)。IPC(送信 → エンジンが読む)p50 0.12ms / p99 0.34ms
  - 負荷テスト(4レーン + EQ + リミッタ + オートメーション、ブロック 512)
    - **実デバイス**(WASAPI「スピーカー (USB Audio Device)」、出力レイテンシ 22ms、マスターゲイン 0 で無音): 590秒でアンダーラン **0**(PortAudio の output_underflow)、コールバック負荷 平均 12%・最大 38%
    - **NullBackend**(1ブロックの締め切りに間に合わなければアンダーラン、という実デバイスより厳しい判定): 590秒でアンダーラン **3**。3件とも t=317秒付近の約1.3秒間に集中しており、その間はスレッドの起床が 3〜9ms 遅れ、コールバックも 6〜10ms かかっていた(ほかの時間帯はアンダーランなし、GC の実行時刻とも無関係)。エンジンの外で起きた一時的な CPU 競合と判断。同じ条件の 180秒の実行ではアンダーラン 0、起床遅れ最大 1.0ms
  - 経緯: 最初の 10分テストは PC がスリープして無効(Windows の Kernel-Power 42 で確認)。2回目・3回目はアンダーラン 12・11 だったが、そのとき私(Claude)の待機ループが Git Bash 経由で 5秒ごとにプロセスを起動していた。待機ループをやめ、上記の GC/優先度の対策を入れた後が 3件
- **判断**: 指示書 12章の「NullBackend で 10分間アンダーランゼロ」は、この開発機では厳密には未達(外部要因の 1.3秒間に 3件)。実デバイスでは 10分間ゼロを達成。NullBackend の判定をデバイス並みに緩める(バッファを持たせる)ことは、目標を後から動かすことになるのでしていない。`scripts/load_test.py`(`--device` で実デバイス・無音)と `tests/test_load.py`(既定 5秒、`CLIDJ_LOAD_SECONDS=600` で 10分)で再測定できる

## D13. 先読み時間の既定値: 200ms

- **決めたこと**: `[audio] lookahead_ms = 200`(既定)。UI のスケジューラは「エンジンの位置 + 200ms」までに来る予約の Thunk を評価し、予定の拍を付けてエンジンへ送る
- **実測**(`scripts/measure_lookahead.py`: ヘッドレスの Textual アプリで、4レーンに毎拍 `every(0.25, Ln << s)` を予約し、0.25秒ごとに `queue()` を打ちながら 30秒ずつ。NullBackend)
  - UI 描画の最適化(D12)の前: ティック間隔の最大が実行を重ねるごとに 87 → 261ms と悪化(GC の全世代走査と、1文字ずつの Rich 描画)。遅れて届いたコマンドは 先読み 0ms: 156/157、50ms: 24/161、100ms: 12/161、200ms: 4/161(最大 19ms 遅れ)、300ms: 0
  - 最適化の後: ティック間隔 p50 33.3ms・p99 36〜41ms・最大 41〜49ms で安定。先読み 50 / 100 / 150 / 200 / 250 / 300ms のどれでも遅延到着 0/245
  - 必要量の見積もり: UI ティックの最大 49ms + 1ブロック 10.7ms + IPC 0.3ms ≈ 60ms
- **理由**: 見積もりの約3倍の余裕を取り、指示書の目安 150〜300ms の中に置いた。ヘッドレス計測には実ターミナルへの書き出し時間が入っておらず、セットの読み込みやバックグラウンドの解析と重なることもあるため。先読みを長くすると「予約の評価が早くなり、その後の変数の再代入が反映されない時間」も長くなる(README に明記)ので、300ms 以上にはしない
- 遅れて届いたコマンドはエンジンが件数と最大遅延を数え、UI に表示する(フェーズF)
