## 1. このプロジェクトは何か

ターミナル上でライブコーディング的にDJをするツール。

- パフォーマンス前に、曲から短いパーツ(スニペット。DJでいう tools)を切り出して用意しておく
- 本番では、共通の時計(Transport)の上に「何小節目に、どのスニペットを、どう重ねる/つなぐか」を Python 風のコードで書く
- コマンドは原則として小節頭などの区切りにクオンタイズされ、タイピングが遅れても音楽的には必ず揃う
- 事前に書いたセットファイル(`.djs`)を流しつつ、REPL から割り込んで書き換えられる
- 見た目は ghostty 風のペイン分割 TUI(左: ライブラリ、右上: コンソール、下: トランスポートとレーン)

現在のリポジトリは、この思想を「音の鳴らないビジュアルシミュレーション」として実装し終えた状態。
Transport / Snippet / Lane / Scheduler / ast ベースの安全なインタプリタ / Textual の TUI / pytest 64本がある。

今回のゴールは、これを本物の音が鳴る DJ ツールにすること。

## 2. 最初にやること

1. リポジトリ全体(README.md の設計メモを含む)を読む
2. `pytest` を実行して全部通ることを確認する
3. この指示書を読んだうえで、フェーズごとの実装計画を `docs/plan.md` に短く書く(各フェーズで作る/変えるモジュール、主要なインターフェース、テスト方針)
4. 計画の中で、この指示書と矛盾する点や、実際に動かしてみないと決められない点があれば `docs/plan.md` の冒頭に列挙する。致命的でなければ、妥当と思う案で進めてよい

## 3. 絶対に守る原則

以下はどのフェーズでも破らないこと。迷ったらここに戻る。

1. 時刻の正はオーディオのサンプルカウンタだけ。UI の壁時計やティックで音のタイミングを決めてはいけない
2. 音楽的な位置の正は「拍」。サンプル位置は、テンポマップを通して拍から計算する派生値として扱う
3. スケジュールされた出来事(スニペット開始・停止・オートメーション開始)は、予定された拍に対応するサンプルちょうどに起きる。ブロック境界ではなく、ブロック内のオフセットまで正確に
4. オーディオコールバックの中では、ファイル I/O、ロック待ち、ログ出力、大きな配列の確保、pickle、例外の送出をしない
5. 重い処理(解析、タイムストレッチ、ファイル読み込み)は、事前準備としてオーディオと別の場所で行い、結果をキャッシュする。本番中にリアルタイムでストレッチしない
6. 音が止まる・プツッと鳴ることは、機能が足りないことより重いバグとして扱う
7. 音を聴けない前提で、正しさは数値で検証する(オフラインレンダリング+自動テスト。10章)
8. 音声デバイスがない環境でも、ビジュアルのみのモード(`--no-audio`)と全テストが動く
9. 既存の思想(スニペット、クオンタイズ、特殊形式による遅延評価、安全なインタプリタ)は維持する。コマンド言語の後方互換はできる限り保つ

## 4. 技術的な前提と決定事項

### 実行環境
- 開発者の環境は Windows(`py` ランチャー、`.venv\Scripts\...`)。Windows で動くことが第一条件。Linux/macOS はテストが通れば十分
- Python は 3.12 以上に上げる(現状の README は 3.11 前提)
  - 理由: 2026年9月時点で numpy 最新(2.5系)と librosa 1.0 系が Python 3.12 以上を要求するため
  - 3.12 と 3.13 のどちらにするかは、依存パッケージの Windows 向け wheel の有無を確認して決め、`docs/decisions.md` に記録する

### ライブラリ(この指示書を書いた時点で動作を確認した候補。採用前に最新の状況を自分で確認すること)
- 音声ファイルの読み込み・リサンプリング: `pedalboard.io.AudioFile`(WAV/FLAC/MP3/AIFF/OGG)
- タイムストレッチ: `pedalboard.time_stretch`(Rubber Band ベース、Windows 向け wheel あり)
  - 出力長は `入力長 / stretch_factor` ちょうどにはならない(48000サンプルを 128/124 倍速にして 46500 サンプルになり、計算上の約46452とずれることを確認済み)。必ずレンダリング後に正確な長さへ揃える処理を入れる(6章)
- EQ・リミッタ: `pedalboard` のフィルタ類(LowShelfFilter / HighShelfFilter / PeakFilter / HighpassFilter / LowpassFilter / Limiter など)、または scipy の IIR を自前で状態付きで回す。どちらを使うかは 7章の要件を満たせるほうを選ぶ
- BPM・ビート検出: `librosa.beat.beat_track`(1.0 系)。キー検出は `librosa.feature.chroma_cqt` とキープロファイル照合で自前実装してよい
- オーディオ出力: `sounddevice`(PortAudio。Windows では WASAPI を優先して試す)
- TUI: 既存どおり Textual
- 新しい依存を追加するときは、Windows 向け wheel があること、メンテされていることを確認する

### 既定値(設定ファイルで変更可能にする)
- サンプルレート 48000 Hz、ブロックサイズ 512、ステレオ、float32
- 先読み(lookahead)は 8章で決める値を既定にする

## 5. フェーズA: 前回レビューで見つかった問題の修正

実オーディオに進む前に直す。いずれも回帰テストを先に書いて、失敗することを確認してから直すこと。

1. ルーラーと波形の位置ずれ
   - ルーラーはペインの横幅全体の中央に ▼ を置いているが、波形はレーン名・role・key の後ろの狭い範囲に描かれ、その範囲の中央をプレイヘッドにしている。▼ と実際のプレイヘッドが20文字ほど離れ、小節線も波形と対応していない
   - さらに中央の計算が波形側 `width // 2`、ルーラー側 `round(width / 2.0)` で異なり、奇数幅で1文字ずれる
   - 列 ↔ 拍の変換を1つの関数にまとめ、ルーラーと全レーンの波形が同じ左端・同じ幅・同じ中央を使うようにする
2. スニペット開始拍とオートメーション開始拍が区切りちょうどにならない
   - 発火時点の `transport.position_beats` を使っているため、発火したティックの分だけ後ろにずれる。デモセットで L3 が 64.0711、L4 が 128.0711 から始まることを確認済み(128BPM で約33ms)
   - 予約イベントは「予定された拍」を開始拍として使う。xf の開始拍・終了拍も同様。実オーディオではこれがサンプル単位の正確さの前提になる
3. `kick = snip(...)` で作ったスニペットの名前が変数名にならず、`snip1`, `snip2` … になる。`name=` 未指定のスニペットを代入したときは変数名を名前にする
4. `after(-4, 式)` のように過去を指すと、イベントがキューに残り続けて永遠に発火しない。負の値はエラーにする
5. `start()` 前に `at(1, 式)` を書くと「過ぎている」扱いで2小節目に回される。Transport 停止中で、指定位置が現在位置と同じ場合は、開始した瞬間に発火させる
6. `every(極端に小さい値, 式)` で1ティック内の発火ループが回り続けてアプリが固まる。最小間隔を1拍(0.25小節)にし、スケジューラの1ティックあたりの発火数にも安全上限を設ける
7. セットファイルの中で自分自身を `load_set` すると、ログを199行出したあと再帰上限エラーになる。読み込みのネスト深さに上限(例: 8)を設け、わかりやすいエラーにする
8. ライブラリの TRACKS タブで、列の余白込みの幅が枠に収まらず Time 列が隠れ、横スクロールバーが出ている
9. LANES ペインは高さ 1fr だが実際には6行程度しか使っておらず下半分が空いている。レーン1本あたり2〜3行で波形を描き、拍の頭が目で追えるようにする
10. ログの整理
    - 予約から発火したコマンドが「L2 << snip2 (now)」と表示され、`now()` を使ったように見える。予約発火は別の表記にする
    - 「L1 now playing …」が「L1 << … 」より先に出る順序の逆転を直す
    - `at` / `after` / `every` で予約したとき、何小節目に予約されたかをログに出す

## 6. フェーズB: ライブラリと解析

フェイクの `DEMO_LIBRARY` を、実際の音声ファイルに置き換える。フェイクライブラリは `--demo` / テスト用に残す。

### ライブラリ
- 設定ファイル(例: リポジトリ外のユーザー設定ディレクトリの `config.toml`。場所は決めて記録)にライブラリのフォルダを複数指定できる
- トラックの識別子は内容から作る安定したID(ファイルサイズと先頭・末尾の一部のハッシュなど)。ファイルを移動しても解析結果が失われないこと
- REPL で使いやすいよう、一覧上の短い番号も引き続き使える(`snip(3, ...)`)。番号は安定IDに解決される

### 解析(トラックごとに1回、結果をキャッシュ)
- BPM とビートグリッド: EDM など一定テンポの曲を前提に「BPM + 最初の拍の位置(秒)」で表す
- キー: Camelot 表記
- 波形ピーク: 既存の `SAMPLES_PER_BEAT = 16` と同じく拍基準の解像度で保存(UI の波形表示用)
- ラウドネス: 統合ラウドネス(LUFS 相当)
- フレーズ単位の自動キューポイント(既存ロジックを拍グリッド基準で流用)
- 解析はバックグラウンドのワーカープロセスで行い、UI を止めない。進捗を UI に表示する
- 解析結果の手動補正を別ファイル(overrides)に保存し、自動解析より優先する。自動解析は必ず外れる前提で設計する

### コマンド追加
- `scan()` ライブラリの再スキャンと未解析トラックの解析
- `regrid(3, bpm=127.98, offset_ms=12)` グリッド補正(overrides に保存し、そのトラックのレンダリングキャッシュを無効化)
- `setkey(3, "8A")` キー補正

## 7. フェーズC: スニペットのレンダリング(事前準備)

スニペットは「再生時にストレッチする」のではなく、「現在のセットBPM用に事前にレンダリングしたバッファ」として扱う。

### レンダリング手順(要件)
1. 元ファイルから、スニペット範囲(拍 → 秒はそのトラックのグリッドで変換)に前後の余白(例: 1拍ずつ)を足して読み込み、エンジンのサンプルレートに揃える
2. `stretch_factor = セットBPM / 元BPM` でタイムストレッチする
3. 余白を取り除き、長さを `length_beats × 60 / セットBPM × サンプルレート` サンプルちょうど(整数に丸めた値)に揃える。丸め誤差がループのたびに累積しないよう、ループ再生時の位置計算は拍基準で行う
4. ループしないスニペットは先頭と末尾に数ミリ秒のフェードを付ける。ループするスニペットは継ぎ目でクリックが出ないよう、末尾を先頭に短くクロスフェードさせる
5. ラウドネスを目標値に揃えるゲインを計算して保持する(バッファに焼き込むかどうかは判断に任せる)

### キャッシュ
- キャッシュキー: トラックID、グリッド(overrides 込み)、スニペット範囲、ループ有無、セットBPM、サンプルレート、レンダラのバージョン
- 形式は float32 の `.npy` などにし、エンジン側は `numpy.load(mmap_mode="r")` で読めるようにする(プロセス間でバッファをコピーしないため)
- 置き場所はリポジトリ外のキャッシュディレクトリ。`.gitignore` にも念のため追記

### 準備の流れ
- `snip()` を評価した時点で、レンダリングジョブを準備ワーカーに投げる(非同期)
- `prep()` 定義済みの全スニペットを現在のBPMでレンダリングし、完了まで進捗を表示
- SNIPS タブに各スニペットの準備状態(未 / 中 / 済 / 失敗)を出す
- 準備が済んでいないスニペットを再生しようとしたら、そのコマンドは「準備完了後の最初の区切り」まで保留し、警告を出す。無音で再生を始めてはいけない

### BPM 変更
- `bpm(x)` は、使用中・予約中・定義済みのスニペットを新しいBPMで先にレンダリングし、全部揃ってから最初の小節頭で切り替える
- 切り替えの瞬間、各レーンは「スニペット内の拍位置」を保ったまま新しいバッファに乗り換える
- 準備中である旨と、切り替わる予定の小節を表示する

## 8. フェーズD: オーディオエンジン(オフライン)

まずデバイスなしで、決定的に WAV を書き出せるエンジンを作る。これが以降すべての検証の土台になる。

### 構成
- `Engine` は次を持つ: テンポマップ(拍 ↔ サンプル、BPM 変更点を含む)、サンプルカウンタ、レーンプレイヤー(N本)、ミキサー、コマンド受け口
- エンジンへのコマンドは「適用する拍(または即時)」付きのデータ(`EngineCommand`)。インタプリタや Thunk のような Python オブジェクトはエンジンに渡さない
  - 例: スニペット開始(レーン、レンダリング済みバッファの参照、開始拍)、レーン停止(拍)、ゲイン/ミュート/EQ 変更(即時、平滑化付き)、オートメーション(対象、開始拍、終了拍、始値、終値、カーブ)、BPM 変更(拍)
- ブロック処理では、ブロック内に適用拍が含まれるコマンドをサンプルオフセットで分割して適用する
- 即時のパラメータ変更は、数ミリ秒のランプで平滑化してジッパーノイズを出さない
- xf などのオートメーションはサンプル(少なくとも数ミリ秒)単位で補間する

### ミキサー
- レーンごと: ゲイン、ミュート、3バンドEQ(DJミキサー的に lo/mid/hi をそれぞれ 0.0〜1.0 で絞れ、0 でほぼカット)
- マスター: マスターゲインとリミッタ。出力が 0 dBFS を超えないこと
- 既存の警告(キー相性、vocal の重複、BPM 乖離)は引き続き出す

### オフラインレンダリング CLI
- `python -m clidj render sets/demo.djs --bars 48 -o renders/demo.wav` のように、セットファイルを実時間を待たずに最後まで流して WAV を書き出せる
- 途中で REPL から打つコマンドを模擬するため、「何小節目にこのコマンドを入力した」というスクリプトも渡せるようにする(テストで使う)
- `renders/` は `.gitignore` に入れる

### テストの原則(10章も参照)
- テスト用の音源は、テスト内で合成して一時ディレクトリに書き出す(著作権のある音源をリポジトリに入れない)
- クリック音(インパルス)を正確な拍位置に置いた合成トラックを使えば、開始位置・揃い具合をサンプル単位で数値検証できる

## 9. フェーズE: リアルタイム化

### プロセス構成
- オーディオエンジンは専用の子プロセスで動かす。UI(Textual)と同じプロセスのスレッドにしない
  - 理由: Textual の描画やインタプリタの処理が GIL を保持している間、オーディオコールバックが待たされ、10ms 程度のブロックでは音切れが起きやすいため
  - Windows の spawn 方式で動くこと
- エンジンプロセスの中では、コールバックと、コマンドを受け取ってコールバック用の構造に積むスレッドを分ける。コールバックはロックを取らない構造(atomic な deque の pop など)から読むだけにする
- UI プロセス → エンジン: コマンドのキュー
- エンジン → UI: 共有メモリで「現在のサンプルカウンタ、拍位置、BPM、各レーンの状態、メーター値、アンダーラン回数、コールバック処理時間」を公開。UI は描画のたびに読むだけ
- レンダリング済みバッファはファイル経由で共有する(7章の mmap)

### オーディオバックエンドの抽象化
- `SoundDeviceBackend`(実デバイス)、`NullBackend`(デバイスなしで実時間ペースでコールバックを回す。CI やデバイスのない環境用)、`OfflineBackend`(8章、実時間を待たない)
- `--list-devices`、`--device 名前または番号`、`--no-audio`(ビジュアルのみ。現在のシミュレーション動作を維持)

### 先読みスケジューリング
- インタプリタとスケジューラ(特殊形式の Thunk を持つ部分)は UI プロセスに残す
- スケジューラは、発火予定の拍が「現在位置 + 先読み時間」以内に入った時点で Thunk を評価し、結果を `EngineCommand` として予定の拍付きでエンジンへ送る。エンジンはその拍のサンプルで正確に適用する
- 先読み時間の既定値は、UI 側のティック間隔とプロセス間通信の遅延を十分に吸収できる値(目安 150〜300ms)にし、実測して決めて記録する
- この方式により、Thunk は予定の拍より少し早く評価される。先読み時間内に変数を再代入しても反映されないことを README に明記する
- エンジンにコマンドが予定のサンプルより遅れて届いた場合は、次のブロックの先頭で適用し、遅延量をログに出してカウントする(音楽的には失敗なので、UI に目立つ表示を出す)
- `now(式)` は「エンジンが受け取った次のブロック」で適用する
- 停止中の Transport に対するコマンドは即時適用でよい

### 表示と遅延補正
- UI のプレイヘッド位置は、エンジンの位置から出力レイテンシ(ストリームが報告する値)を引いた「今聞こえている位置」を表示する
- ステータス表示: デバイス名、サンプルレート、ブロックサイズ、レイテンシ、アンダーラン回数、コールバック負荷(処理時間 / ブロック時間)

### 終了処理
- Ctrl+C、`quit()`、UI の異常終了のいずれでも、エンジンプロセスが残らないこと
- エンジンプロセスが落ちたら UI に表示し、UI 自体は落ちないこと

## 10. フェーズF: UI 統合

- 波形は解析済みのピークデータを使う
- LIBRARY の TRACKS に解析状態、SNIPS に準備状態を出す
- ステータス行(9章)を TRANSPORT の行か専用の行に出す
- 先読み・準備待ち・遅延到着の警告を、ログだけでなくレーン表示にも反映する
- フェーズAで直したルーラーと波形の整列が、実データでも保たれていること

## 11. 検証とテスト

音を聴けない前提で、以下を自動テストにする。許容誤差は目安で、根拠を持って調整してよい(調整したら記録)。

### 解析
- 合成クリックトラック(例: 124BPM、最初の拍 0.37秒)で、BPM 誤差 ±0.1 以内、最初の拍の位置 ±10ms 以内

### レンダリング
- 124BPM の合成トラックから 8小節を 128BPM でレンダリングしたとき、長さが計算値ちょうど
- 出力内のクリックの位置が、128BPM の拍位置から ±3ms 以内(ストレッチによるトランジェントのにじみを考慮)
- ストレッチなし(同 BPM)のときはサンプル単位で一致
- ループの継ぎ目・スニペット端で、隣接サンプル間の差分が閾値以下(クリックがない)

### エンジン(オフライン)
- 128BPM・48kHz で `at(3, L1 << a)` と `at(3, L2 << b)` を予約すると、どちらのクリックも 3小節目頭 = 180000 サンプル目ちょうどから始まる
- 途中で `bpm()` を変えても、切り替え後の拍位置がテンポマップどおり
- xf の中間地点で、一定振幅の信号のゲインが期待値 ±0.01 以内
- 即時のゲイン変更でジッパーノイズが出ない(差分の閾値)
- 4レーンを最大ゲインで重ねてもマスター出力のピークが 1.0 以下
- EQ の lo=0 で、低域のサイン波がほぼ消える(例: -30dB 以下)

### リアルタイム
- `NullBackend` でエンジンプロセスを起動・コマンド送信・状態の読み出し・終了ができる(CI で実行)
- 先読みスケジューラが、Thunk を予定拍の先読み時間以内にだけ評価すること
- 遅延到着の検出とカウント
- エンジンプロセスを強制終了したとき、UI 側が例外で落ちない

### 手動確認用のレンダリング
- 自動テストとは別に、`renders/` に人間が聴いて確認するための WAV を数本書き出すスクリプトを用意し、「何小節目で何が聞こえるはずか」を `docs/listening-checklist.md` に書く(クロスフェードの自然さ、ループ継ぎ目、ストレッチの質など、数値で判定しにくいもの)

### 既存テスト
- 既存の 64 本はフェーズ間で壊さない。設計変更で意味が変わるテストは、意図を保ったまま書き換え、書き換えた理由をコミットメッセージに書く

## 12. パフォーマンスの目安

- コールバック処理時間はブロック時間の 50% 未満を平常値とし、超えたらステータスに警告
- 4レーン同時再生・EQ 有効・リミッタ有効で、ブロックサイズ 512 のとき 10分間アンダーランゼロ(`NullBackend` の実時間ペースで計測する負荷テストを用意)
- UI の描画は 30fps を目安にし、描画が重くても音には影響しないこと(プロセス分離で担保)

## 13. 進め方と記録

- フェーズ A → B → C → D → E → F の順。各フェーズの終わりで全テストを通してからコミットする。コミットは意味のある単位で細かく、メッセージは英語
- `git push` は開発者から指示があるまでしない
- 設計判断は `docs/decisions.md` に「決めたこと / 検討した他の案 / 理由」を短く追記していく。とくに次の項目は必ず記録する
  - Python のバージョン
  - EQ とリミッタの実装方法
  - 先読み時間の既定値と実測値
  - キャッシュと設定ファイルの置き場所
  - 許容誤差を調整した場合の根拠
- この指示書どおりにやると明らかにまずい点に気づいたら、無理に従わず、`docs/decisions.md` に理由を書いたうえで良い方を選ぶ。ただし 3章の原則を変える場合は、実装に進む前に作業を止めて開発者に確認する
- README は各フェーズで、実際に動く状態に合わせて更新する(起動方法、依存、Windows でのセットアップ、コマンド一覧、セットファイルの書き方、既知の制限)

## 14. やらないこと(今回のスコープ外)

- ヘッドホン用のキュー出力(2系統出力)。ただし出力チャンネルの割り当てを後から足せる構造にはしておく
- MIDI コントローラ対応
- テンポが途中で揺れる曲(可変テンポ)のビートグリッド
- 本番中のリアルタイムストレッチ
- ステム分離
- 外部の遷移データ(自動ミックス生成プロジェクト)との連携。ただしスニペット定義を外部から生成して流し込めるよう、`snip()` 相当の処理を UI やインタプリタから独立させた状態を保つ

## 15. 完了条件

- Windows で README の手順どおりにセットアップし、自分の音声ファイルのフォルダを設定して `scan()` すると、解析が進み、TRACKS に BPM・キー・解析状態が出る
- 実音源で書いたセットファイルを読み込み、`prep()` 後に `start()` すると、スニペットが小節頭ぴったりに入り、`xf` でクロスフェードし、`L1.eq(lo=0)` で低域が抜ける音が実際にスピーカーから鳴る

- `bpm()` の変更が、準備完了後の小節頭で音切れなく切り替わる
- 画面の波形とルーラーが揃い、プレイヘッドが今聞こえている位置を指している
- 10分間の再生でアンダーランが出ない(ステータス表示で確認できる)
- `--no-audio` と `render` サブコマンドが動く
- `pytest` が全部通り、デバイスのない環境でも通る
- `docs/plan.md`、`docs/decisions.md`、`docs/listening-checklist.md`、更新済みの README がある
