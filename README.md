# cli-dj (snippet-driven live coding, visual-only prototype)

ghostty風にペイン分割されたターミナル上のDJツール。「曲を2枚かけて手でつなぐ」のではなく、
事前に切り出した短いスニペットを、共通の時計(Transport)の上で **コードとして** 展開していく
スタイルを目指しています。FoxDot/TidalCycles のようなライブコーディング環境が近い見た目です。

**音は一切鳴りません。** 波形・BPM・再生位置はすべてシミュレーションで、実際のオーディオ
デコード/再生・BPM解析は行っていません(そのための設計上の空き所は残してあります。後述)。

## 起動

Python 3.11 以上が必要です(このリポジトリは `py -3.11` で作った `.venv` を想定)。

```bash
py -3.11 -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python app.py
```

デモセットを流し込んで起動する場合:

```bash
.venv\Scripts\python app.py --set sets/demo.djs
```

`--set` は起動時にそのファイルの中身をそのまま実行するだけです。**Transport は自動では
開始しません** — 起動後にコンソールで `start()` と打つまで無音(無進行)のままです。

## 画面構成

```
+-- LIBRARY ------------+-- CONSOLE ------------------------------+
| [TRACKS] [SNIPS]      | ログ                                     |
|                       |------------------------------------------|
|                       | QUEUE  #3 @033.1 xf(L1, L4, 8)           |
|                       | > 入力欄(↑↓で履歴)                        |
+-----------------------+------------------------------------------+
| TRANSPORT  033.2  ● RUN  128.0 BPM  4/4  q:bar                   |
| ルーラー    |···|···|···|···▼···|···|···|···|···                  |
| L1 kick   drums 8A  (プレイヘッド中央固定のズーム波形)  gain  loop 3/8 |
| L2 bass   bass  8A  ...                                          |
| L3 —                                                             |
| L4 —                                                             |
+------------------------------------------------------------------+
```

- **LIBRARY**: `TRACKS`(曲一覧)と `SNIPS`(定義済みスニペット一覧)をタブで切り替え
- **CONSOLE**: ログ、予約中イベントの QUEUE(発火順に最大5件)、コマンド入力欄
- **TRANSPORT / LANES**: 小節.拍・再生状態・BPM・クオンタイズモード、ビートルーラー、
  L1〜L4 各レーンの状態。ズーム波形はプレイヘッドを中央に固定し、左(過去)はレーンの色、
  右(未来)は灰色。1文字 ≈ 1/4拍なので、全レーンの拍の頭が縦に揃って見えます。
  相性が悪いスニペット同士が同時に鳴っているレーンは名前が黄色になります。

## コマンド言語

右上の入力欄に打ってEnter。指定がなければ次の区切り(デフォルトは小節頭)で実行される
**クオンタイズ**が基本です。Python の式として構文解析されますが、`eval`/`exec` は一切
使わず、許可した構文とホワイトリストの関数/メソッドだけを自前で辿って実行します。

| 書き方 | 意味 |
|---|---|
| `start()` / `stop()` | Transport を開始 / 停止 |
| `bpm(128)` | Transport のBPMを変更(次の小節頭で反映。停止中は即時) |
| `quant("bar")` | デフォルトのクオンタイズ変更(`beat`/`bar`/`phrase`/`none`) |
| `kick = snip(1, cue=2, bars=8, loop=True, role="drums")` | スニペット定義(曲はID/タイトルどちらでも) |
| `hook = snip("Glass Horizon", bar=33, bars=4, role="vocal")` | 小節番号指定の例 |
| `L1 << kick` / `L1.play(kick)` | 次の区切りで L1 に kick を流し始める |
| `L1.stop()` | 次の区切りで L1 を止める |
| `L1.gain(0.5)` / `L1.mute()` / `L1.unmute()` | 音量操作(即時) |
| `L1.eq(lo=0, mid=1, hi=0.8)` | EQ値の変更(見た目のみ、即時) |
| `xf(L1, L2, bars=8)` | 次の区切りから8小節かけて L1→L2 にクロスフェード |
| `at(33, 式)` | 33小節目の頭で式を実行(区切りに関係なく、指定した小節そのもの) |
| `after(4, 式)` | 次の小節頭から数えて4小節後に式を実行 |
| `every(8, 式)` | 8小節ごとに式を実行(`cancel`で停止) |
| `now(式)` | クオンタイズせず即実行 |
| `queue()` | 予約中イベントをログに出す |
| `cancel(3)` / `cancel()` | ID 3 のイベントを取り消す / 全取り消し |
| `snips()` | 定義済みスニペット一覧 |
| `load_set("demo")` | `sets/demo.djs` を読み込んで実行 |
| `clear()` / `help()` | ログのクリア / コマンド一覧表示 |

`at`/`after`/`every`/`now` は特殊形式で、中の式(第2引数)は書いた時点では実行されず、
実際にその小節が来たときに初めて評価されます。`at(33, xf(L1, L2, 8))` と書いても、
`xf(...)` がその場でクロスフェードを始めることはありません。

## セットファイル

拡張子 `.djs`。中身はコマンド言語そのもの(`#` から行末はコメント)。`sets/` 直下に置いて
`load_set("名前")`(拡張子なし)で読み込むか、`python app.py --set sets/名前.djs`(パスその
まま)で起動時に読み込みます。`sets/demo.djs` に一例があります:

```python
bpm(128)

kick  = snip(1, cue=2, bars=8, loop=True, role="drums")
bass  = snip(8, bar=17, bars=8, loop=True, role="bass")
hook  = snip(3, bar=33, bars=4, loop=True, role="vocal")
riser = snip(5, bar=25, bars=8, role="fx")
drop  = snip(5, cue=3, bars=8, loop=True, role="drums")

L1 << kick
at(9,  L2 << bass)
at(17, L3 << hook)
at(25, L4 << riser)
at(33, L4 << drop)          # riser が終わる小節で drop に差し替え
at(33, xf(L1, L4, bars=8))  # 同じ小節の予約は書いた順に実行される
```

`python app.py --set sets/demo.djs` で起動して `start()` と打つだけで、この展開が
小節頭ごとに自動で進みます。

## 構成

ロジック(`transport`/`library`/`snippets`/`lanes`/`scheduler`/`interpreter`)は Textual に
依存しません。Textual を import するのは `app.py` だけです。

- `transport.py` — 全体の時計。`position_beats` を唯一の時刻源として持ち、小節/拍/クオン
  タイズ境界の計算をすべてここに集約
- `library.py` — フェイクの曲データ。波形・キューポイントは拍単位(`amplitude_at_beat`)
- `snippets.py` — 曲からスニペットを切り出す `snip()`。長さは必ず拍の整数倍、曲長超過は
  エラー
- `lanes.py` — L1〜L4。再生位置は毎回 Transport から計算し直す(状態を持たない = 累積誤差
  や「戻る」バグが構造的に起きない)。キー相性/役割衝突/BPM乖離の警告もここ
- `scheduler.py` — クオンタイズ付きスケジューラ。`at`/`after`/`every`、`xf` のゲイン
  オートメーションもここ
- `interpreter.py` — ast ベースの安全なインタプリタ。`eval`/`exec` は使わない
- `app.py` — Textual製TUI本体
- `sets/demo.djs` — デモセット
- `tests/` — pytest 一式

## 設計メモ(判断の記録)

指示書にない/曖昧だった点、または一見小さく見えて実は効いてくる判断をここに残します。

- **フェーズ0のバグ修正は「直してから消す」ではなく新設計に直接織り込みました。**
  `Deck`/`commands.py` はどのみち今回のフェーズ3・5で丸ごと置き換わるため、旧コードに
  パッチを当ててから捨てるのは二度手間と判断しました。各項目の対応先:
  - ループのラップ不具合 → [`Lane.local_beat`](lanes.py) が毎回 `position_beats` から
    `local % length_beats` を計算するだけなので、そもそも「前回の位置」という状態を持たず
    構造的に再発しません(回帰テストは `tests/test_lanes.py` に置いてあります)
  - クロスフェーダーの値が見えない → TRANSPORT/LANESパインの各レーンに `gain` メーターを表示
  - 波形が曲全体を1行に圧縮していて拍が見えない → 拍単位の波形データ+ズーム表示で解決
  - `sync()` が瞬間コピーで追従しない/位相が合わない → 全レーンが Transport 基準で位置を
    計算するため、この概念自体が不要になりました
  - `cue()` で再生が止まる → 新しいコマンド体系に実行時の `cue()` は存在せず(`snip()`の
    `cue=` は曲を切り出す位置の指定であって再生コマンドではない)、該当しません
  - `[`/`]` がキュー番号を上書きする → 波形表示自体を全面刷新したため非該当
  - ライブラリ幅でTime列が切れる → DataTable の各列に明示的に `width=` を指定して解決
  - コンソールが広すぎる → CONSOLE/LANESとも `height: 1fr` でおおよそ半々に
  - 固定dt前提 → `time.monotonic()` の実差分を `Scheduler.tick(dt)` に渡す方式に変更

- **`at(33, L1 << kick)` のように、スケジュール済みの式の中でさらに別のコマンドを呼ぶ場合、
  その内側のコマンドはアンビエントな量子化を二重にかけません。** `Interpreter` に
  `_in_scheduled_context` フラグを持たせ、`at`/`after`/`every`/`now` が式を評価している間は
  `L1 << kick` や `xf(...)` を即実行に切り替えています。これがないと「33小節目に予約した
  はずが、中の `L1 << kick` がさらに『次の小節』を待って34小節目から鳴る」という、
  スケジューラ二重掛けのズレが起きます(`tests/test_interpreter.py` の
  `test_command_inside_at_does_not_requantize_a_second_time` で確認)。

- **属性アクセスはメソッド呼び出しの位置でしか許可していません**(`L1.gain(0.5)` は
  可、裸の `L1.gain` を式の値として使うのは不可)。指示書のホワイトリスト方針を最小実装
  で満たすための単純化です。今回のコマンド言語ではメソッド呼び出し以外の用途がないため
  実害はありません。

- **`snip()` の `bar=` は 4/4 前提の固定 `BEATS_PER_BAR = 4`** を `snippets.py` に持たせ、
  意図的に `Transport.beats_per_bar` から独立させています。これは「曲(素材)側の小節」の
  話であって、生成される Snippet はライブセット側の Transport の拍子とは無関係に有効な
  はずなので、别系统にしました。

- **`every(n, ...)` は最初の発火を「次の小節頭」から数えます**(呼んだ瞬間の小節ではなく)。
  `after(n, ...)` も同様に「次の小節頭から n 小節後」です。どちらも指示書に厳密な定義が
  なかったため、"次の区切りに対する相対指定" で統一しました。

- **フェイクのキューポイント(`cue=1..4`)は曲の頭寄りに集まりがちです**(8小節フレーズ
  ×1,2,3 を曲長でクリップする式のため、長い曲ほど後半のキューが使われません)。見た目上の
  デモデータの癖であり、実データ(実BPM解析)に差し替える際は再検討が必要です。

- 開発機の既定 Python は 3.10 でしたが指示書が 3.11 以上を要求しているため、
  `py -3.11 -m venv .venv` で専用の仮想環境を作りました。システム既定の `python` を
  そのまま使うと動きません。
